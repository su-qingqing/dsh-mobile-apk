### 4.4 keystore 与签名策略（结论）

**现状**：仓库只有 `keystore/debug.keystore`（2,618 B，md5 `ade7e7b2…`），别名 `androiddebugkey` / 口令 `android` / store `android`。`app/build.gradle.kts:49-60` 定义 `repoDebug`，`debug` buildType 挂它；v38 的 `release` **未挂任何签名配置**。

**策略**：

1. **自测/自用档**：`assembleDebug`，签 repoDebug（v1+v2+v3）。与现役 v51 证书一致 → `adb install -r` 直接覆盖。
2. **发布档**：给 `release` 也挂 `signingConfigs.getByName("repoDebug")`（v0.14.8 已把 `enableV1Signing/V2/V3 = true` 写死在 repoDebug 里，注释明写"所有交付 APK 强制包含 v1/v2/v3 签名"）。
3. **不要**生成新 keystore —— 一旦换 key，覆盖安装必然 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，只能卸载重装，**`home/.dsh`（含 731 MB 跨窗库 + 19 个用户插件 + 4.6 GB home）全丢**。
4. `keystore/debug.keystore` 已随仓库公开（GitHub 可拉到同一个文件），仅用于自签自用；若要上架分发需另建 release key，但**那会断开与 v51 的覆盖链** —— 本轮不做。

## 5 · 问题④："在跑旧货"怎么根治

### 5.1 现状证据链（本次实测）

1. **生产件确实在设备上被反复就地改**：`dsh-kickoff-gate/lib/index.js` 旁留了 **17 份 `.bak-*`**（0926 ×3、0927 ×2、0928 ×2、1001 ×4、1015 ×2、1019、1020、1021、1023），现役 `index.js` 139,238 B / md5 `7cbd07f5…` / mtime **2026-10-23 11:40**。
2. **现役进程启动时间**：`$F/.public-repo-status` = `ok|engineStart|1793057763091|…` → **2026-10-27 07:36:03**（`$F/.plugin-soft-manifest.json.lastProbeBoot = 1793057762943` 同刻）→ **晚于 10-23 11:40**，即本次启动加载的是 10-23 那版，`kickoff-gate.log` 末行 `armed(3.4 · …) on tools/pre-execute + tools/post-execute` 也证明它已挂上。**本轮此刻没有在跑 0926 旧货**（0926 备份是 88,525–91,100 B，与现役 139,238 B 明显不同）。
3. **但机制上完全没有防线**：改完到生效全靠"记得重启 + 重启成功了"。
4. **用户插件不进构建链**：v0.14.8 的 `scripts/profile-web.cordis.patch.yml` 里 `@dsh-user` 出现次数 = **0**；`scripts/plugin-dirs.json`（v0.14.8）的 `dirs` = 3 个顶层包（`dsh-shell-termux` / `dsh-client-ui-responsive` / `dsh-host-web-compat`）+ 6 个 `@dsh-android`，`externals` = 2 个（undo / marketplace）——**所有 `@dsh-user`（含 kickoff-gate）都不在任何门禁视野内。**
5. **hard manifest 不含它们**：`.plugin-hard-manifest.json` 205 条全为 `@deepseek-ai/@dsh-android/vendor`；`@dsh-user` 只出现在启动时探测的 soft manifest 里，而 soft 只记 `names`（28 个字符串）+ 一个整体 `digest`，**不记单文件 sha256** → 改没改、跑的是不是改过的，机器无从判断。

### 5.2 根因三层（**并纠正一处误判**）

| 层 | 根因 | 证据 |
|---|---|---|
| A｜配置层 | `$B/profiles/web/package.json` → `"dsh": { "profile": { "patchReload": "startup" } }` —— **补丁只在启动时重载** | 实测该文件 320 B |
| B｜装配层 | 双真源：仓库权威 16,998 B vs 真机现役 63,056 B（删 75 / 增 744），仓库侧所有门禁都看不见那 744 行 | §3.4 |
| C｜构建层 | `@dsh-user` 不在 `plugin-dirs.json`、不在注入链、不在 hard manifest → 改了没有"构建号"可比对 | §5.1-4 |

> **纠正**：`analyze/out/发现.md` ①说"真根因是插件缺 `inject`"。实测 `inject` 是 **package.json 里 `dsh.client.inject` 的客户端 UI 注入目标声明**（例：`dsh-session-manager` 写 `"inject":["@deepseek-ai/dsh-client-ui-sidebar-right"]`；`dsh-android-bridge` 写 `["@deepseek-ai/dsh-client-runtime","…-ui-settings"]`）。而 `dsh-kickoff-gate` 的 package.json 自述"**纯宿主、零界面、fail-open**"，**它本来就不该有 inject**。所以"缺 inject"不是 kickoff-gate 不生效的原因；真正的原因是 **A+B+C 三层**。（19 个 `@dsh-user` 里 6 个有 inject、13 个没有，与"是否生效"无对应关系。）

### 5.3 要加的 5 道机制（保证"改了必生效"）

**M1 · 构建号内嵌（buildId 单一来源）**

- `app/build.gradle.kts` 已有先例 `buildConfigField("String","TERMUX_VERSION","\"0.118.3\"")`（:31）→ 增加：
  ```kotlin
  buildConfigField("String", "BUILD_ID", "\"${System.getenv("DSH_BUILD_ID") ?: "local-" + System.currentTimeMillis()}\"")
  ```
- 引擎侧已有 `DSH_APP_VERSION`（注释 :28-29 明说"版本号单一来源…引擎环境变量 DSH_APP_VERSION，见 EngineManager.engineEnv"）→ 同一处再挂 `DSH_BUILD_ID`。
- 每次构建生成 `assets/build-id.txt`，与 `snapshot.sha256` 同目录，由 `check-snapshot-fingerprint.mjs` 那类门禁顺带断言存在。

**M2 · 用户插件进 hard manifest（逐文件 sha256）**

- 扩展 `.plugin-hard-manifest.json` 为 `schema:3`，新增 `entries` 里所有 `@dsh-user`（19 个 × package.json + lib/**），字段：`{id, name, path, sha256, bytes}`。
- 生成脚本（新增）：`scripts/gen-plugin-user-manifest.mjs`，输入 `user-plugins/@dsh-user/`，输出 `app/src/main/assets/plugin-user-manifest.json`。
- 现有 `check-snapshot-fingerprint.mjs` 的写法（"sha256 实际值 == 声明值，逐字节"）直接复用为模板。

**M3 · 启动 drift 自检（改了没生效 → 立刻红字，而不是静默）**

- 新增 `scripts/check-runtime-freshness.mjs`（PC 侧）+ 壳启动/开窗时跑的设备侧自检：
  1. `assets/build-id.txt` vs `$F/.last-boot-build-id` → 不一致 = 刚升级，提示"本次为新版首次启动"；
  2. 逐文件比对 `$B/profiles/*/node_modules/@dsh-user/**` 的 sha256 vs M2 的 manifest → 不一致 = **漂移**；
  3. 再比 `cordis.patch.yml` 的 sha256 vs 仓库权威版 → 双真源漂移量**首次可量化**（今天只能人工 diff）。
- 输出落到 `$F/.plugin-drift.log` + **开窗注入块顶部红字**（不是写进台账让她自己发现）。

**M4 · 构建链门禁扩展到 `@dsh-user`**

- `scripts/plugin-dirs.json` 增加 `"user": [...]` 段；
- `scripts/inject-all.py` / `inject-external-plugins.py` 增加 `--dsh-user <dirs>`（后者已支持 scoped，见 §3.3）；
- `scripts/check-inject-completeness.mjs` 读 `dirs+externals` → 改成 `dirs+externals+user`（它现在从 `plugin-dirs.json` 读，一行改动）；
- `scripts/check-patch-mounts.mjs` 的双向差集自动覆盖 `@dsh-user`（"注入了没挂载"/"挂载了没注入"两向）；
- `scripts/ci-verify-snapshot.py` 现有断言"快照内 cordis.patch.yml 必须与权威版同长同内容"——**这条正是防双真源的**，把它从 CI 前移到本地构建必跑。

**M5 · 装配清单改为"只读生成物 + user overlay"**

- 每次启动由壳把 `assets` 里的权威 `cordis.patch.yml` 写回 `profiles/*/cordis.patch.yml`（或至少写一份 `cordis.patch.repo.yml` 做影子比对）；
- 她的改动落到新增的 `cordis.patch.user.yml`（overlay），启动时 merge；
- 这样"改了"永远发生在**仓库里能回灌的位置**，而不是设备上一个 63 KB 的无人审计文件。

> M1/M2/M4 是**构建期**可立刻做的（本次方案范围内）；M3/M5 涉及壳侧 Kotlin 与引擎加载，**需要 App 侧专家共同定稿**，本方案只给出落点与判据。
